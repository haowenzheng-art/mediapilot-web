## 2. 本次会话修复清单（7 个）

### ✅ #31 修复 copywriting_service user_id=0 硬编码

- **根因**：`copywriting_service.generate()` 在持久化时硬编码 `user_id=0`，导致 FK 约束失败，任务终态始终 failed
- **改动 6 处**（按数据流方向）：
  - `services/copywriting_service.py:30,75` — `generate()` 增加 `user_id: int` 必传参
  - `worker.py:113` — 调用时传 `user_id=user_id`
  - `worker.py:115-127` — `model_dump(mode="json")` 解决 datetime 序列化
  - `api/copywriting.py:147` — 同步路由传 `user_id=user.id`
  - `services/agent_service.py:222-247, 322-343` — 两个 Tool 加 `user_id` kwarg
  - `services/agent_executor.py:102,167` + `api/agent.py:53,151` — user_id 从认证用户一路透传到工具调用
- **验证**：提交任务 → ARQ 入队 → Worker 拾取 → DB 持久化（user_id=4）→ 终态 completed

### ✅ #32 统一注册接口 email 字段 schema

- **根因**：`RegisterRequest.email: str` 与下游 `UserCreate.email: Optional[EmailStr]` 类型不一致，Pydantic 静默转换失败时返回 500 而非 422
- **改动**（`backend/api/auth.py`）：
  - L7 import：`from pydantic import BaseModel, EmailStr, Field`
  - L25-29 RegisterRequest：`email: EmailStr` 强类型，username/password 加 min/max length
- **验证**：畸形邮箱 422 / 合法邮箱 200 / 缺字段 422 / 空字符串 422

### ✅ #33 修复转写引擎初始化失败 coverage.types Tracer

- **根因**（与最初推测不同）：不是 MediaPilot 代码 bug，是 **numba 与 coverage 的版本冲突**
  - numba 在 `numba/misc/coverage_support.py:114` 顶层执行 `class NumbaTracer(coverage.types.Tracer)`
  - coverage 7.4.0 把 `Tracer` 重命名为 `TracerCore`
  - `import whisper` 间接触发 numba 加载，抛 `AttributeError`
- **改动**（`backend/core/transcribe_engine.py:56-69`）：
  - 捕获元组加 `AttributeError`
  - warning 日志带异常类型和消息
- **验证**：日志从"转写引擎初始化失败"红字变成"whisper_local 不可用，回退到 mock 模式"正常降级
- **未做的环境层修复**（运维决策）：`pip install 'coverage<7.4'` 或 `pip install -U numba`

### ✅ #34 Agent 工具失败被 LLM 吞掉假装成功

- **根因**：工具返回 `{"success": false}` → executor JSON 序列化喂给 LLM → LLM 仍以乐观口吻输出 Final Answer
- **修复策略**（三层防御）：
  - 数据层 `agent_executor.py`：收集 `tool_failures`；失败 observation 包装成 `[TOOL_FAILED] ... 你必须在最终答案中如实告知用户该步骤失败的原因`
  - 协议层：`success = not tool_failures`，trace 中标记 `failed: True`
  - 接口层 `api/agent.py`：`/run` 200 时 data 带 tool_failures；500 时 error.detail 带 tool_failures；`/stream` SSE 每事件带 failed 标志
- **验证**：要求 LLM 用 `mode=broken_mode_xxx` 调 generate_copywriting → LLM 老实尝试 2 次 → 最终回答诚实告知"工具调用失败，原因是 mode 不符合 pattern" → API 顶层 success=False，error.tool_failures 完整保留

### ✅ #37 修复 task_queue.py main 模块导入路径错误

- **改动**：`from main import arq_pool` → `from backend.main import arq_pool`（2 处）

### ✅ #38 修复 ARQ Job 状态查询 API 误用

- **根因**：原代码用 `arq_pool.ainfo_job()`，这是不存在的 API
- **改动**：改用 `from arq.jobs import Job, JobStatus`，通过 `Job(task_id, redis=arq_pool).status()` + `result_info()` 查询

### ✅ #39 修复 ARQ enqueue_job 缺少 _job_id 参数

- **根因**：ARQ 自动生成 job_id，前端用业务 task_id 查不到任务（返回 not_found）
- **改动**：两个 enqueue_job 调用都加 `_job_id=task_id`
- **附带修复**：去掉 `_job_timeout=300`（ARQ 会把它当作 worker 函数参数透传，导致 `unexpected keyword argument`），用 Worker.job_timeout 配置项替代

### ✅ #40 修复 worker 函数名不匹配 + response_model 类型冲突

- **根因**：
  1. Worker 注册用字符串 `"backend.worker.generate_copywriting_job"`，enqueue 用短名 → ARQ 匹配不上，返回 `function not found`
  2. `@router.get("/{task_id}", response_model=dict)` 但路由返回 `APISuccessResponse` 对象，Pydantic 校验失败
- **改动**：
  - `worker.py`：`functions = []` 占位，模块底部 `Worker.functions = [generate_copywriting_job, search_trending_job]` 注册 callable
  - `task_queue.py`：移除 `response_model=dict`

### ✅ #41 配额仅在 worker 完成时扣减，提交时不预扣

- **根因**：
  1. `task_queue.submit` 用 `if op and not auth_service.check_quota(...)` 把 `Tuple[bool, int]` 当 bool 用，永远真值 → check 形同虚设
  2. 即使 check 通过，没有预扣，恶意用户可无限刷队列任务
- **改动 4 处**：
  - `auth_service_typed.py`：新增 `refund_quota` 方法
  - `task_queue.py submit`：check + 立即 deduct；enqueue 异常或不支持类型时 refund
  - `worker.py generate_copywriting_job` 失败分支调 refund
  - `worker.py search_trending_job` 失败分支调 refund
- **验证**：
  - 提交后立即扣减（100→95）
  - 任务成功不重复扣（仍 95）
  - 失败任务扣 + worker 退还（95→90→95）
  - 余额耗尽返回 429（连续 19 次成功扣减，第 20 次 HTTP 429）
